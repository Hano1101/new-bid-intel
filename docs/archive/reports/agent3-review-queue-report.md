# 创新点 #3：人工复核队列（第一版）

> 历史报告，已于 2026-10-11 归档。正文保留当时的结论和验证范围；当前实现请查阅[项目文档索引](../../DOCUMENTATION_INDEX.md)。

## 队列规则与排序

队列根据当前数据集中的候选和公告记录即时生成，不读取模型置信度，也不调用模型。候选只有在至少命中一条规则时才进入队列：

- 标的物字段为空，且保存状态为未知或未核实；已由完整字段证据确认的“原文未公示”或“来源留空”不会按缺失项重复提示。
- 标的物字段有值，但字段来源证据不完整或状态未核实。字段证据要求同时保存来源文件、原文定位和来源片段。
- 标的物、投标或中标记录缺少来源片段、来源文件或原文定位。
- 包号为 `default`，提示这是系统占位值，需要核对原公告。
- 公告中的警告可归入 OCR、解析回退、解析失败、附件格式或附件展开等已有警告类别。公告级警告会作为上下文关联到该公告的候选，并在队列项中原文显示。
- 标的物的数量、单价和总价都能解析为有限十进制数时，如果“数量 × 单价”与总价不相等，则列出可复算的冲突说明。

排序依据固定规则优先级，再按公告 ID、候选类型（标的物、投标记录、中标记录）和候选 ID 排序。优先级分为三档：来源或数值冲突、字段缺失或解析告警、`default` 包号。每个队列项显示命中的具体原因和优先级说明；没有概率分数或模型置信度排序。

第一版不把项目名称、采购单位或预算金额的缺失单独作为候选队列项；不以预算金额和中标金额是否相等推断冲突；不尝试关联后台失败任务，因为失败任务与已保存候选没有可靠的逐条标识映射；不推断违法、围标或串标结论。数量×单价采用精确十进制相等比较，折扣、税费或舍入造成的合理差异仍需人工判断。

## 决定记录与数据隔离

每个数据集的 SQLite 库各自保存 `review_events` 表。事件保存候选类型和 ID、候选代次、决定、理由、操作人、UTC 时间、首份复核时的原始候选及来源快照、修改前值、修改后值和字段差异。候选表发生删除（包括替换导入时的级联删除）时，复核模块的本地 SQLite 触发器递增该候选 ID 的代次；新候选即使复用了整数 ID，也不会继承旧决定或待处理状态。决定请求必须带页面读取到的候选代次，服务端在事务内校验，旧页面不能把决定写入已替换的新候选。历史接口保留并返回各代次的事件，界面会标明已替换候选的历史版本；前端历史缓存也按代次区分并在新增决定后刷新。后续决定继续追加事件，并以前一次复核值作为同一代次新的修改前值；完全重复的决定返回 409。登录开启时操作人来自已验证会话；本地开发模式使用固定标识 `local-reviewer`，请求体中的操作人字段会被拒绝。

接受、修正、驳回以及后续修正都只写复核事件，不更新候选表。修正值是独立的复核覆盖记录；候选的原抽取值、包关联、分析结果、Gold、holdout 和评测产物不会因此自动改变。包号修正也不会调用包号归一化或更改数据库中的包关联。

所有队列、决定和历史 API 都使用现有 `X-Dataset-ID` 数据库依赖。候选和事件分别位于该数据集自己的 SQLite 文件中；未提供请求头时使用 `default` 数据集。错误或未知的数据集 ID 不会回退到默认库。

队列读取在同一 SQLite 事务内获取原始候选、事件和候选代次，避免并发替换导入把旧候选值与新代次拼接。前端按数据集请求版本丢弃迟到响应；处理末页后自动回退到最后有效页，刷新队列时也重新读取已打开的历史。

## API 与界面

- `GET /api/v1/review-queue?status=pending|processed|all&candidate_type=item|bid|award&limit=50&offset=0`：筛选和分页。默认只返回待复核项，单页上限为 200。
- `POST /api/v1/review-queue/{candidate_type}/{candidate_id}/decisions`：记录 `accepted`、`corrected` 或 `rejected` 决定。理由必填；队列返回的 `candidate_epoch` 会随请求提交并在服务端校验，候选被替换时要求刷新。修正字段按候选类型白名单验证，来源、身份、置信度和抽取元数据不可修改。
- `GET /api/v1/review-queue/{candidate_type}/{candidate_id}/history`：读取该候选按时间追加的事件历史。
- 页面入口：左侧“分析应用”下的“人工复核队列”。候选上的“查看公告与来源”会打开现有公告证据弹窗；弹窗展示候选、来源片段、文件清单和 OCR/解析警告。原始文件字节不由当前存储层保留，因此入口展示已保存的证据，不承诺重新打开原文件。

## 手工验收

1. 启动后端与前端，登录评审账号；在“数据集管理”中新建一个仅用于验收的数据集。
2. 导入一份包含标的物表格的测试公告及附件。选择能触发字段缺失、未验证字段、`default` 包号或 OCR/附件解析警告的数据；不要使用 Gold 或留出评测数据。
3. 打开“人工复核队列”，检查候选类型、项目和包信息、原始字段值、每条触发原因、优先级、来源片段状态和相关警告。
4. 点击“查看公告与来源”，核对弹窗中对应公告、候选来源和警告。对于没有来源片段的记录，页面应明确显示“无来源片段”。
5. 分别对候选接受、修正、驳回并填写理由；修正后检查变化前后值、操作人和时间。确认“待复核”中该项消失，在“已处理”或“全部状态”中查看决定，并打开复核历史。
6. 在另一个数据集查看同一类型队列和历史，确认刚才的候选决定不可见；返回验收数据集，确认其历史仍在。
7. 重复发送同一决定应收到 409；尝试提交非法动作、伪造操作人或修改来源/置信度等字段应收到 422。
8. 在队列页面保留一份待复核表单，替换导入该公告后再保存旧表单，应收到要求刷新候选的 409。刷新后新候选仍待复核；历史中旧候选事件带历史版本标记。

实现主要新增 `backend/app/review_queue.py`、`frontend/src/components/ReviewQueue.vue` 及相应测试与工具函数；`main.py`、`App.vue` 和导航仅作路由/组件接线。实现没有调用真实模型 API，也没有改动抽取 prompt、归一化、候选合并、Gold、holdout、评测器或标注工作台。现有未提交改动已保留，未提交或 push。

## 已知限制

- 队列项由现有保存字段和公告警告构成；第一版没有把后台任务失败事件映射到候选，也不会扫描原始文件重新提取证据。
- 复核覆盖值保存在对应候选代次的历史中供审核查看，不会传播到关系表、搜索结果、分析、Gold 或评测结果；这些产物需要后续由明确流程处理。升级前已经存在、但没有候选代次字段的旧事件只能统一视为代次 1，无法从历史数据恢复更早的删除/复用关系。
- 来源弹窗只能展示已保存的片段、定位和文件哈希状态。当前数据层不保存来源文件字节，历史文件无法保证可重新打开。
- 字段缺失规则可能把适用性需要人工判断的空字段排入队列；精确金额关系检查也可能把折扣、税费或舍入差异列为提示。
- 前端自动化使用 Vue `compileScript` 和自定义 `createRenderer` 运行组件实际 setup/actions，验证筛选分页、三种决定、只提交修改字段、错误与重复决定、迟到响应及历史刷新；辅助函数验证缺少证据、默认包号、OCR/附件告警和来源跳转。组件测试以空 render 运行，未使用真实浏览器或覆盖完整 DOM/端到端展示。
- 队列每次读取当前数据集全部候选，再排序和分页；首版未做大数据量性能验收。读写复核表时使用短 SQLite 写事务，与并发导入会按 SQLite 规则串行。
